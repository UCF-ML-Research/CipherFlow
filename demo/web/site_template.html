A hardware-aware compiler framework for efficient secure inference

Private inference splits a model between homomorphic encryption and secure multi-party computation. CipherFlow finds the split for your hardware and network: for every operator of a PyTorch model, where it runs, where to convert, and where to bootstrap.

How it works

From a PyTorch model to a placement plan

CipherFlow plans against an abstraction of the backends: methods, each one operator in one domain with the CKKS levels it consumes, the inputs it accepts and its measured cost. A library plugs in by registering its methods and a cost profile, or by declaring its primitives.

Three ideas behind the planner

MicroBench

Costs measured where you deploy

Every operator, conversion and bootstrap is timed on the target hardware, with its bytes and rounds, so the plan follows measured costs instead of a fixed rule.

State expansion

One search over domains and levels

Each operator's state is its domain and, in HE, the CKKS levels left. Placement, conversions and bootstraps become one shortest-path search over these states.

BlockFold

Residual blocks folded into steps

Each residual block is a single-entry, single-exit region. Folding it into one step contains the growth from branching joins and keeps planning tractable on Transformer-scale graphs.

Backends

Measured HE and MPC backends

Each backend reports its methods and the measured cost of every operator, conversion and bootstrap. CipherFlow plans with each pair of backends that fits the deployment and keeps the best plan.

Homomorphic encryption

  • ✓OpenFHE CKKSAll operators on one 128-bit parameter set, fast and precise bootstrapping, hardened HE↔MPC conversion, wide-range GeLU, Softmax and LayerNorm
  • ✓NEXUSSEAL on CPU, Phantom on CUDA; reference-scaled costs

Secure multi-party computation

  • ✓SCI / BOLT (EzPC)Two parties, no third party; CPU
  • ✓SHAFT (CrypTen)Two parties and a trusted dealer; CPU and GPU
  • ○SPUCheetah and SEMI2K; planned

    Tutorial 1
    
        
    Plan a model, step by step
    
        
    A plan says, for every operator, whether it runs in HE or MPC, how many CKKS levels it uses, and what converts or bootstraps before it. This tutorial plans the demo's BERT-base encoder. Install from source and run it from the repository root.
    
      
    
      
      
        
    1. 
          1
          
      Step 1: Trace the model
      
            
      from_torch traces your encoder with torch.fx and maps it onto CipherFlow's operators: the Q/K/V projections, QKᵀ, Softmax, Attn·V, the linear layers, LayerNorm, GeLU and the residual adds. Each operator keeps its place in your code.
      
            
      An operation outside this set raises cf.UnsupportedModel, which names each one.
      
          
      Python
      import torch
import cipherflow as cf
from demo.transformer import bert   # BERT-base in plain PyTorch

encoder = bert()
graph = cf.models.from_torch(encoder, torch.zeros(1, 128, 768))
for node in graph.nodes[:4]:
    print(node.op_type, node.input_shape, node.attributes["source"])

      Step 2: Describe the deployment
      
            
      A deployment is the server's hardware and the network between the client and the server. cpu and gpu select the built-in cost profiles. Give the network as bandwidth / round-trip time, or measure it with cipherflow netbench.
      
            
      cf.match shows which HE and MPC backend pairs can plan the model there. The default security model, 2pc, allows two parties and no third party.
      
          
      Python
      # hardware profile; network as bandwidth / round-trip time
deployment = cf.Deployment.of("cpu", "10Mbps/1ms")
print(cf.match(graph, deployment))   # HE + MPC pairs that fit

      Step 3: Compile
      
            
      compile plans the model with each backend pair that fits and keeps the best plan. It searches each operator's domain and CKKS level together, so it places conversions and bootstraps where they cost least.
      
            
      plan.alternatives lists the other pairs and their latencies.

      plan = cf.compile(graph, deployment)

      Step 4: Read the plan
      
            
      explain(steps=True) lists the operators in execution order. Each row gives HE or MPC, the CKKS level before and after, and the line of your PyTorch code. The conversions and bootstraps that run before an operator sit above it.
      
            
      Here Softmax runs in MPC, between two conversions, and everything else stays encrypted.

      Step 5: Save it and check it on real data
      
            
      plan.json holds the whole plan for other tools. emulate runs the model in float64 with each operator in its planned domain: the HE kernels' approximations, fixed point in MPC, and each conversion's rounding. It runs at plaintext speed and does not run the cryptography.
      
            
      Calibrate on real inputs with cf.runtime.calibrate, and pass the calibration to compile. Operators whose values fall outside an approximation then stay out of HE.
      
          
      Python
      plan.to_json("plan.json")      # cipherflow explain plan.json --steps
x = torch.randn(1, 128, 768)   # hidden states of a real input
result = cf.runtime.emulate(plan, encoder, x)
print(result.summary())
      Output
      output vs plaintext: max |err| 0.017, relative 0.00248
conversions 24, bootstraps 59 executed (plan: 24 / 59)

    Tutorial 2
    
        
    Bring your own applications & primitives
    
        
    CipherFlow is not tied to the models and backends it ships with. Bring a faster kernel, a library's primitives, or an application with a step of its own; declare what one call costs, and the planner places it as it does the built-in ones. Each card shows the layer your code goes into. The examples continue the tutorial above: graph is BERT-base and deployment is a CPU server at 10 Mbps / 1 ms; each has a demo to run from the repository root.
    
      
    
      
    
        
        
        
      
    
      
    
        
    Run the demo
    python -m demo.extensions.new_he_primitive

ext.primitive("Softmax", "HE",
              levels=4,                                    # CKKS levels one call consumes

plan = cf.compile(graph, deployment, he="openfhe-fast", mpc="sci", extensions=[ext])
print(plan.explain(steps=True))

    Run the demo
    python -m demo.extensions.private_rag
    
        
    Python
    from torch import nn

class TopK(nn.Module):                                # scores -> indices of the k largest
    def __init__(self, k):
        super().__init__()
        self.k = k
    def forward(self, scores):
        return torch.topk(scores, self.k, dim=-1).indices

class Ranker(nn.Module):
    def __init__(self):
        super().__init__()
        self.encoder, self.head, self.topk = bert(2), nn.Linear(768, 768), TopK(4)
    def forward(self, x):
        return self.topk(self.head(self.encoder(x)))

topk = cf.Extension("my-topk").operator(TopK, "TopK")
topk.primitive("TopK", "MPC", cost=cf.Cost(local_ms=120, comm_bytes=8_000_000, comm_rounds=40))
ranker = cf.models.from_torch(Ranker(), torch.zeros(1, 128, 768), extensions=[topk])
plan = cf.compile(ranker, deployment, he="openfhe-fast", mpc="sci", extensions=[topk])
print(plan.explain(steps=True))

    Plans use the costs and levels you declare, as given. CipherFlow does not check an extension's correctness, precision or security, and does not execute extensions yet.

    Roadmap
    
    
    From encoders to generative models
    
    
    BERT and ViT encoders are done. Generative models come next, first the backend operators decoders need and then the models; after them, a runtime that executes plans under encryption.
